## 对先前结论的修正

双方都是 OAuth。差别包括客户端注册、申请/实授权限、可用账号元数据和服务端请求上下文；并不是“OAuth 与非 OAuth”的差别。

时屿当前使用独立 SIWC 动态注册和公共 API 资源。OpenAI 官方 Token reference 文档描述该流程的 `aud` 为公共 API，认证元数据应作为不透明数据处理；这本身不能证明某个其他端点必然拒绝，也不能拿来解密认证元数据。

官方参考：`https://developers.openai.com/siwc/token-sharing-open-source/token-reference`。

之前单次探针只检查 **Access Token** 中的可读 `chatgpt_account_id`，当时不能据此推断保存的 **ID Token** 一定没有账号 ID。明确授权后的本轮新增诊断已在手机进程中检查当前账号的加密记录，两类令牌均未取得该可读字段。只输出存在与否，不导出身份字段，不用解析结果扩大权限。

401 尚未证明具体原因；不能断言补一个请求头必定成功，也不能说所有 OAuth 都无法读取窗口。同样，读到 5h/7d 只证明该账号的对应窗口被返回，不能拿作其他授权链路或其他产品的统一额度解释。

## 新增专项

`Sub2ApiQuotaCompatibilityTest` 只在 androidTest 中，不改变生产网络、客户端注册、账号或 UI。

三个已通过的本地专项分别验证：

1. 真实字段缺失时不猜测 ID，允许诊断从 ID Token 元数据识别候选字段，拒绝换行注入。
2. 参考请求头不改变 bearer 和账号，不注入 Cookie 或 OAuth client ID；仅使用虚构令牌测试。
3. 状态码优先分类：401/403 非 JSON 仍为 HTTP 拒绝，重定向和挑战分别标记。此修正只在新增诊断中；旧探针及生产代码未据此宣称已修复。

真实方法为 `compareExistingGrantWithReferenceHeaders`，必须显式传入 `quotaProbe=sub2api-header-compare`，默认不执行。本次明确授权已用于一次执行，不代表允许反复运行。

已执行的对照仅复用同一枚现有令牌，对固定官方端点发送两次应用层 GET：普通请求头与参考 Codex 请求头。两个请求使用相同的账号候选提取规则；Access/ID Token 均无该字段，故均未发送账号头，并报告 `MISSING_ACCOUNT_ID`，明确不是 sub2api 完整链路复现。未修改客户端、扩大 scope、借其他客户端身份重新授权、复制 Cookie、跟随重定向、使用代理、调用推理或消费重置次数。不读取任务数据，不输出原始响应。

即使参考头请求得到 200，也只说明该组合在本次有效，尚需独立接口、缓存/错误处理与隐私测试才能交付生产直读。两次都失败也只排除“只补这些请求头即可”的假设，不能证明完整 Codex 兼容认证一定不可行。
